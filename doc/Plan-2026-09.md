# Plan: numeric core and syntax, September 2026

Three Claude Code sessions, one plan. This document is the coordination
point: each session reads it once at start, works its own section, and
records milestones in its `## Status` block at the bottom of its repo's copy.
The detailed specs it draws on are `diluvium-numeric-spec.md` and
`diluvium-syntax-proposals.md`, committed beside it; this file states what
is decided, in what order, and how the sessions hand off without waiting on
each other.

Commit this file and both specs to `doc/` in diluvium and in diluvium-drt.
The lab session reads them from diluvium.

## 0. Read this first

### 0.1 Spend

Read this plan and the two specs once. Then read only the files your
milestone names. Do not survey the repository, do not spin up exploratory
agents to "understand the codebase", and do not re-derive decisions this
plan already made. Subagents are for exactly two things: running the full
cross-target gate in parallel at a milestone boundary, and one review pass
of a milestone's diff before it merges. Everything else is one agent,
sequential. Measure before you believe a number, but measure once and write
it down. Prefer the existing gates (`examples/run-all.sh`, `expected.txt`,
the diluvium test suite) over new harnesses. When a task is done, say so in
one line in `## Status` with the commit hash, and move on. Under-explaining
is fine; the code and the gate are the record.

### 0.2 Decide, record, proceed

When a question comes up that this plan does not answer, choose the option
most consistent with section 1's principles, write one line under
`## Decisions` in your `## Status` block, and continue. Do not stop to ask.

Stop and wait for the owner only for these:

- A change to `dv.h` beyond what section 3 declares.
- Anything that would make a valid Lua 5.5 program parse or behave
  differently (the freeness test in 3.6 is the check).
- Any change to the behavior of a shipped DRT connector, or any edit under
  the WireGuard, tunnel, relay, TURN, STUN or netcheck code. Those just
  started working in the field; they are not touched this round.
- Any change to how `drt-config` parses a field that exists today. New
  fields are added beside existing ones, never by reworking a shared path,
  and the loader corpus in 3.8 is the check. Every shipped install runs a
  config this loader wrote; a regression here is not caught by any other
  gate.
- A new dependency that adds more than 1 MB to any artifact, or any
  dependency with a non-permissive license.
- Anything that would change the dump/undump format or add an opcode.

### 0.3 Branches and merges

Each session works on one branch (`numeric-syntax` in diluvium, `numeric`
in diluvium-drt, `syntax-highlighting` in lab). Merge to `main` at a
milestone only when the full gate passes on every target CI runs. Never cut
a release or move a tag; leave CHANGELOG entries as `status: unreleased`.
The owner releases.

## 1. What we are building, and the principles that decide ties

Diluvium gains typed arrays, portable numeric kernels, an embedded libm
that makes float transcendentals bit-identical across targets, FFT and NTT,
and a set of syntax additions. DRT gains a `features` compatibility fact,
a raw-buffer lane in the hostcall reply, a parquet/CSV connector, and the
config surface that bounds numeric work per instance. The lab and homepage
gain highlighting for the new syntax and a size ledger for the web profile.

Principles, in the order they win ties:

1. **100% Lua compatibility.** Every new syntax form is a parse error in
   stock Lua 5.5. No new opcodes; desugars emit existing bytecode.
2. **Determinism is reported, not enforced**, except where a program opts
   in (`<deterministic>`). Bit-identical across native, wasm, browser and
   Windows is the reproducible tier's contract.
3. **Core patches minimal**, maintained as the patch series against
   upstream. Everything expressible through `lua.h`/`lauxlib.h` is on-top C.
4. **Feature-gated.** A build without `numeric` is byte-identical to today.
   `slim` stays exactly what it is.
5. **Nothing here needs a new build every four hours.** The shipping DRT
   release path is untouched; this work lands behind a flag and a pin.

Out of scope this round, do not build or explore: GPU backend, yieldable
kernels, the dataframe/stats/ML dlua packages (a later session, see 7),
braces, inline type annotations, Tier D syntax, decQuad (not a dependency
of anything here; arrays are `f64`/`i64`/`u8`).

## 3. Interfaces between sessions

These are fixed so no session waits on another to learn a shape.

### 3.1 `dv.h` additions (diluvium publishes in A0, DRT compiles against)

```c
/* Newline-separated feature names this build carries, e.g. "regex\nnumeric".
   Stable for the life of the process. */
const char *dv_features(void);

/* Monotonic build number, the N in 5.5.1_buildN. */
int dv_build(void);

/* Adopt a host-owned buffer into an array value on the instance's stack.
   dtype: 0=f64 1=i64 2=u8. Takes ownership of `bytes`, which must have
   been allocated with the instance's lua_Alloc. Without DV_NUMERIC this
   pushes a Lua string copy instead and returns 1; returns 0 on adoption. */
int dv_array_adopt(dv_instance *inst, int dtype, size_t len, void *bytes);

/* Backend vtable. Declared this round so the shape is fixed; only the
   portable implementation exists. Every entry carries its tier. */
typedef enum { DV_TIER_EXACT, DV_TIER_REPRODUCIBLE, DV_TIER_FAST } dv_tier;
typedef struct dv_numeric_backend {
  int abi;             /* 1 */
  const char *name;    /* "portable" */
  /* function pointers added as kernels land; each paired with a dv_tier */
} dv_numeric_backend;

/* Per-instance numeric bounds and status. */
void dv_numeric_set_max_elements(dv_instance *inst, uint64_t n); /* 0 = none */
void dv_numeric_set_max_tier(dv_instance *inst, dv_tier t);
int  dv_numeric_touched_fast(dv_instance *inst); /* sticky flag for the audit trail */
```

`dv_abi` moves to 2. Rule for `doc/Release.md`: a DRT reports the highest
ABI it speaks and admits any package requiring less or equal.

### 3.2 Hostcall reply blob lane (DRT publishes in B1, diluvium consumes)

The reply struct in `drt-hostcall` gains `blobs: Vec<Vec<u8>>`. A payload
field that carries a column is `{dtype, len, blob: <index>}`. On the C side
`dv_reply_blob(inst, index, &ptr, &len)` reads it, and the connector's Lua
wrapper calls into `array` to adopt. Bytes never pass through the serde
encoding. If the current encoding turns out to be one where this is awkward
(JSON with no side channel), the side channel is added to the reply struct
and the payload references it by index; do not base64 a column.

### 3.3 Output format for cross-target examples

Numeric examples never print floats with `%g`. They print IEEE bit
patterns: `("%016x"):format(string.unpack("<I8", string.pack("<d", x)))`,
or `array.bits(a)` which does the same per element. This is what makes one
`expected.txt` valid on glibc, musl, wasmtime, Chromium and mingw, whose
CRTs format decimals differently.

### 3.4 Budget charging

Kernels charge the instruction budget by element count, never by time:
one instruction per 64 elements processed, checked at block boundaries, so
`exceeded` fires inside a GEMM and the exceed point is identical on every
target (replay depends on this). Session A implements the charging against
the hook in `src/dv.c`; session B exposes `max_elements` and `max_tier` in
the instance config and attenuates them at spawn like budgets.

### 3.5 Build flags for every TU under `numeric` and the embedded libm

`-ffp-contract=off -fno-fast-math -fexcess-precision=standard -fno-builtin`
on every target, including the `cc`-driven builds in `diluvium-sys` and
`drt-web`, and the mingw cross-build. GCC on aarch64 contracts by default;
this is the single most likely cause of a cross-target mismatch. A
"contraction canary" test computes an `a*b+c` whose fused and unfused
results differ and asserts the unfused bits. Never enable wasm relaxed-simd.
Embedded libm symbols are prefixed (`dv_exp`, `dv_sin`) so the compiler
cannot substitute or constant-fold the platform versions.

### 3.6 Freeness check

CI builds pristine upstream `luac` from the tree the patch series applies
to, feeds it `test/syntax/freeness/*.lua` (one file per new form), and
fails if any file parses. The reverse corpus (the Lua test suite plus the
examples) must produce identical output before and after.

### 3.7 Pin protocol

Session A records each milestone's commit hash in its `## Status`. Session
B moves the `diluvium` pin in `Cargo.lock` to that hash at the start of its
next milestone, runs the full gate, and records the result. Session B never
waits on A: every B milestone lists what it does if the pin it wants is not
there yet. Session C reads A's `## Status` for the syntax that has actually
landed and highlights only that.

### 3.8 Config-loader regression corpus

`drt-config` is shared by everything, and B2 and B3 both add fields to it.
Before either, session B captures every config shape that is deployed or
shipped into `crates/drt-config/tests/corpus/`, verbatim, not retyped:
the `wg.host.lua` that `wg.sh` writes on a customer machine (it contains
`connectors = { time = {} }`, an empty map through the `as_array` path
that rc6 fixed for five fields), `examples/deployment.json`, every
`.host.lua` under `examples/`, and the rendezvous config with `peers = {}`.
The test loads each, asserts it parses to the same structure it parses to
today (snapshot on first run), and runs in the examples gate. Any loader
change that fails a corpus file is wrong regardless of what it enables.

## 9. Anticipated blockers, pre-answered

- **`setjmp`/`longjmp` on wasm.** Already lowered in the existing wasm
  builds; kernels raising `lua_error` are fine. Do not redesign error
  handling.
- **Two build systems compile the same C.** diluvium's Makefile and
  `diluvium-sys`'s `build.rs`. Flags in 3.5 must reach both; the canary
  test is how you find out they did not.
- **`-fno-builtin` and the libm prefix.** Without both, the compiler will
  replace `exp(x)` with the platform call or fold constants, and the
  cross-target diff will fail on exactly one target for no visible reason.
- **`%g` on Windows.** Never print decimals in examples; 3.3.
- **wasm SIMD.** `-msimd128` is fine; relaxed-simd is not, ever.
- **The instruction hook.** It clears itself in the pcall-escape case
  (FM-4, upstream, known). Kernels charge the budget through the same hook;
  do not try to fix FM-4 here.
- **Lua's raw metamethod lookup.** Inherited `__tostring`/`__add` are not
  found through `__index`; the class desugar copies them. Already in the
  spec; do not rediscover it.
- **`__eq` on mixed operands.** Silently false in Lua; `array.eq` exists
  for this reason, same as decQuad's note.
- **Empty table ambiguity in DRT's config loader.** `{}` is both empty list
  and empty map; rc6 fixed five fields and every shipped `wg.host.lua`
  carries `connectors = { time = {} }`. The `numeric` block and the
  `columns` list in the `data` connector use the same `as_array`-tolerant
  path, added beside it, and the corpus in 3.8 is what proves the existing
  fields still load. This is the one item in the plan that can break
  installs already in the field.
- **`exec` still stalls the loop.** Not this round's problem and not to be
  fixed in passing.
- **Parquet string columns.** Dictionary-encoded per the spec: `i64` codes
  plus a Lua table of uniques. Do not return a table of strings for a
  million-row column.
- **Expected.txt drift from libm.** Some existing examples may change
  output in the last digits on some target after A3. Update the file, note
  the target and the function in the commit message, move on.
- **Windows `full` does not build.** `data` is `full` only; do not try to
  build `full` for Windows to test it.

### Decisions

- **Rebased onto `main`, which is the golden copy.** `main` moved sixteen
  commits while this branch sat in review, released `v0.15.0`, and landed
  `doc/ALIGNMENT.md` -- a cross-repo versioning proposal at revision 3 with
  review from seven projects, now superseded as the authority by
  `Aloecraft-org/technoproj`. Three collisions, all resolved `main`'s way:
  - **The version scheme.** `50829f61` made Diluvium `2.0.0` with the major
    equal to `DV_ABI_VERSION`. `ALIGNMENT.md` says the opposite in a rule
    with its own heading -- *compatibility is checked by name, never by
    digits* -- and `main` had already shipped `0.15.0` under it. The commit
    is **dropped** and `doc/Versioning.md` with it; `VERSION`, `.technoproj`,
    the changelog and `script/changelog.py` are `main`'s untouched.
  - **`continue`, implemented twice.** `main`'s `8670b2da` and this branch's
    A1 both added it, differing in the label they plant (`"continue"` there,
    `"(continue)"` here). `main`'s survives whole -- parser, lexer, tests and
    prose -- and A1 keeps its other five forms. The `(continue)` argument is
    not lost, only unbuilt: a parenthesised label cannot be spelled in
    source, so a stock-Lua `goto continue` with no visible `::continue::`
    fails to find a target instead of binding to the loop's hidden one.
    That is a two-line change to `main`'s version if anyone wants it.
  - **`_DILUVIUM` and the embedded libm** both install into the same spot in
    `dlibs.c`; unioned, with the libm last as its own comment requires.
  Every recorded hash in this block was rewritten to its post-rebase value;
  the pre-rebase branch is kept at the tag `prerebase-a307328b`.
- **Open: `dv_build()` outlived the counter it reports.** A0 added it to the
  ABI-2 surface as "the N in `5.5.1_buildN`". `main` has since retired build
  numbers, so the function now returns a hardcoded `13` on a `0.15.0` tree,
  with no check left to catch the drift. Three ways out, and this is not
  mine to pick: retire `dv_build()` from the ABI before it ships (session B
  compiles against it and records `diluvium_build` per release, so it is not
  free); keep it and feed it the real version string, which changes its
  declared `int` return; or keep the counter as a build-of-this-version
  number with a source of truth and a check. Owner: whoever cuts the release
  that first carries dv ABI 2.

- **The two specs this plan draws on are in neither repository.**
  `doc/diluvium-numeric-spec.md` and `doc/diluvium-syntax-proposals.md` are
  not in diluvium or diluvium-drt, at any commit either carries. A0 needs
  neither -- sections 2, 3.1, 3.5 and 3.6 specify it completely -- so it was
  done rather than blocked on them. A1 and A2 do need them: this plan
  enumerates A1's Tier A forms and A2's Stage 0 items, but "the canonical
  reduction order exactly as the spec states it" is not recoverable from
  anything committed, and neither is the openlibm subset A3 vendors. Owner:
  the specs need committing to `doc/` beside this file.
- **`diluvium-sys` is in diluvium, not diluvium-drt.** A0 says to read its
  `build.rs` and not edit it, which was written on the premise that it lives
  in B's repository; diluvium-drt's `Cargo.toml` says the opposite in as many
  words ("the language, from its own repo -- diluvium/diluvium-sys stay
  there"). So it is A's file and A applied 3.5's flags to it. It did not
  carry them before.
- **The flags in 3.5 attach to the feature, not to a file.** The numeric code
  lives in `src/dv.c`, which is inside the `onelua.c` amalgamation -- one
  translation unit -- so "every TU under `numeric`" is every TU in a
  `DV_NUMERIC` build. Principle 4 still holds literally: with the feature off
  no flag changes and no define is added, which `make -n` confirms recipe by
  recipe against `origin/main`. Revisit at A2 only if `-fno-builtin` on the
  core measures as a real cost; splitting the TU then is a Makefile change,
  not an interface one.
- **`-fexcess-precision=standard` is probed, the other three are not.** It is
  GCC's spelling and Clang only learned it in 17, so an older Apple clang on
  a macOS runner would fail the build over it. Both build systems probe it
  the same way and drop it the same way. Nothing real is lost: excess
  precision is an x87 phenomenon and no target here (x86-64, aarch64, wasm32)
  has any. The wasm lane does not probe, because `WASI_IMG` is pinned at a
  clang 20.1.
- **`dv_build()` reads a constant in `dv.h`, not a `-D` from the build.**
  Four build systems compile this tree and a define only three of them pass
  is a field that lies in the fourth.
  **Superseded, and now unguarded.** The drift this bought was guarded by
  `script/changelog.py consistency`, which used to fail unless `DV_BUILD`
  agreed with `VERSION`. `main` has since retired the build counter entirely
  (`doc/ALIGNMENT.md` §1, "never put an upstream version in your version
  string"): there is no `DV_BUILD` on `main`, `.technoproj` carries `pre`
  rather than `build`, and `consistency` checks neither. So `DV_BUILD` is a
  hardcoded `13` on a tree whose `VERSION` is `0.15.0`, with nothing left to
  catch it. Owner: see the open question below.
- **`dv_features()` reports only what `dv.c` can state exactly**: `regex`,
  `json`, `msgpack`, `snapshot`, plus `numeric` under the feature. Line
  editing and the threading arm are decided inside other translation units,
  and `dv.c` is compiled both standalone and inside the amalgamation, where
  the two would not see the same macros -- a condition retyped here would be
  a second definition free to drift from the first.
- **`dv_array_adopt` returns 1 in both configurations for now.** 3.1 defines
  1 as "copied into a Lua string", which is what a no-`numeric` build does
  and what every build does until A2 provides an `array` to adopt into. A
  caller written today therefore needs no change when adoption becomes real;
  the return value is how it learns which it got. Invalid arguments also
  return 1, with nothing pushed and ownership not transferred, which the
  header states.
- **The default `max_tier` is `DV_TIER_FAST`.** `calloc` would have made it
  `DV_TIER_EXACT`, silently forbidding every floating-point kernel in an
  instance nobody had configured. The weakest tier is the open default; a
  supervisor narrows it.
- **`dv_reply_blob` is not in `dv.h`.** Section 2's table calls it a `dv.h`
  name, but 3.1 -- the section that says exactly what A0 publishes -- does not
  list it, and 3.2 describes it reading DRT's own reply struct, which
  diluvium has no knowledge of. Taking 3.1 as the authority; it is B1's, in
  DRT's C glue. B: say so if that is wrong and it will be added.
- **`CHANGELOG.yaml` and `VERSION` are untouched.** `changelog.py
  consistency` requires the newest entry to match `VERSION` and
  `.technoproj`, so opening an entry means bumping the tree's version, which
  is a release-shaped action and 0.3 leaves releases to the owner. The ABI
  bump to 2 and the `numeric` feature belong in the entry the owner opens.
- **A freeness file lands with its form, not before.** The check asserts both
  directions -- refused by stock Lua 5.5, accepted here -- because a file that
  is a syntax error everywhere satisfies 3.6's stated half perfectly and
  proves nothing. So `test/syntax/freeness/` holds a file per form that is
  *in* the tree; A1 adds one per form as it lands.
- **The specs arrived mid-session and are committed here.** Both were
  missing from every repository; they are now in `doc/` beside this file,
  verbatim, still carrying their own "draft"/"brainstorm" status lines.
  Where either disagrees with this plan, this plan is the decision.
  Still owed: the same two files in diluvium-drt, which is B's tree.
- **A1's shape is checked by a bytecode diff, not only by the suite.**
  `luac -l -l` over every .lua file in the tree, against the previous
  commit's compiler. It caught a register-allocation bug in the first
  version of the `parlist` rework -- `self` stopped getting a register,
  so every method compiled its first temporary over its last parameter --
  that the whole suite passed straight through. Worth repeating for any
  later parser change.
- **A default parameter may not be combined with `...`.**
  `OP_VARARGPREP` reads the live argument count off the stack, so it has
  to be a function's first instruction; a default's code is already in
  front of it by the time `...` is read, and the lexer is a single pass
  with no way back for the defaults afterwards. Refused with that
  sentence rather than miscompiled. Owner: overrule if the combination
  matters, but it needs the instruction stream rotated, which is lcode
  surgery rather than a parser change.
- **An expression body takes one expression, not a list.** 3.8 says
  "desugar to `return expr end`" and the singular is load-bearing: with
  no `end` to close it, `{ half = function(x) = x / 2, name = "half" }`
  would otherwise read `, name = "half"` as a second return value and
  swallow the rest of the table. A function returning two values keeps
  the block form.
- **Spread is `_ENV.table.unpack`, and two spreads in one constructor are
  refused.** The `_ENV` route follows `defer`, which reaches
  `setmetatable` the same way and documents why; the consequence -- a
  program that replaces the global `table` changes what a spread means --
  is stated in the code rather than hidden. 3.7's helper for multiple
  spreads, and section 2's `dv.spread`, need a registry table that does
  not exist; this one form did not justify building one, so the
  not-last case is a syntax error naming the rule instead of a silent
  truncation to one value. Owner: say if the merge form is wanted and it
  becomes a milestone of its own.
- **`...NAME` means two different things in two places, and both are
  right.** In a parameter list it is 5.5's own named vararg table
  (`function f(...xs)`); in a call or constructor it is 3.7's spread.
  The proposals doc was written without the first. They never meet --
  `parlist` handles `...` itself -- but they read alike, which is worth
  knowing before writing both in one function.
- **Section 8's "keep the sugar in a separate source file" is not
  adopted.** The six forms already in the tree live in `lparser.c` and
  `llex.c`, both long-allowlisted, and splitting them out is a refactor
  A1 was not asked for. Recorded so the next rebase knows the hook points
  were not centralised.
- **A1 shipped a GC hazard and A2's suite found it.** `continue`, `const`
  and the implicit `(continue)` label were never passed to `luaC_fix`, so
  their names could be collected and the memory reused by an unrelated
  name -- after which an ordinary statement was read as a `continue`.
  `switch`, `defer` and `with` were always fixed; the three new ones were
  added in `luaX_setinput` and not in `luaX_init`. Fixed in A2's commit,
  with a regression test in `test_continue.lua` and `test_const.lua`.
  The lesson for A4: a contextual keyword's name is compared by identity
  and has to be as permanent as a reserved word.
- **The budget seam is two functions in `dv.c`, declared in
  `dnumeric.h`.** 3.4 says the charging goes against the hook in
  `src/dv.c`, and only that file can see `dv_instance`. They are not in
  `dv.h`: adding to that header beyond section 3 is on 0.2's stop list,
  and these are not part of the published ABI. `LUA_API` rather than
  `LUAI_FUNC`, following `dshim.h`, because the per-file build compiles
  each `d*.c` without `LUA_CORE`.
- **`min` and `max` follow the ordering rather than skipping NaN.** NaN
  sorts last (spec 4.7), so a NaN never wins `min` and always wins `max`,
  and `min`/`max` are the first and last elements of `sort`. A `max` that
  skipped NaN would disagree with `sort` about which element is largest;
  one rule is worth more than two conveniences.
- **Integer arithmetic on `u8` promotes to `i64`, and comparisons return
  `u8`.** The spec fixes the comparison result (a mask) and says nothing
  about `u8 + u8`; promoting is the reading that does not silently wrap a
  mask into a byte. Recorded because it costs eight bytes per element for
  anyone who does arithmetic on masks, which `where` and `select` exist
  to avoid.
- **Variance is the population one, `var = ss/n`.** The spec says
  two-pass and does not say which denominator. One stated convention
  rather than a `ddof` argument whose default would be the real decision.
- **`__newindex` is added; `__eq` deliberately is not.** The spec lists
  the metamethods as operators and omits both. An array that could not be
  written to would need a `set` call for every element, so `a[i] = v` is
  there. `__eq` is not: two arrays cannot answer `==` with a boolean, and
  Lua's own note (silently false on mixed operands) is exactly why
  `array.eq` returns a mask instead.
- **Two spreads in a constructor and `dv.spread` are still not built.**
  Unchanged from A1; recorded again here because A2 added the `array`
  type that a merge helper would most naturally live beside, and it still
  does not justify a registry table.
- **An array cannot cross a snapshot.** `dsnap` refuses every userdata
  with its existing message; nothing in A2 changed that, and the numeric
  spec does not ask for it. The `__persist` hook is the route if it is
  ever wanted. Worth knowing for B3, whose instances are the ones that
  hibernate.
- **The determinism verdict does not exist, so A3's analyzer half could
  not be done as written.** A3 says to extend the analyzer "so `math.*`
  are no longer taint sources". There is no taint machinery: the verdict
  -- taint sources, call-graph propagation, three values, runtime
  wrappers -- is described in `doc/Analyzer.md` as planned work and none
  of it is code. Nothing to extend. What was done instead is the two
  things that were available: that document's taint list corrected, with
  the measurement behind the correction, and the runtime half's numeric
  flag wired for real and tested. Owner: building the verdict is a
  milestone of its own, not a step inside one, and `doc/Analyzer.md`
  section "What the determinism verdict adds" is already its
  specification.
- **openlibm's licence needs no owner decision.** 0.2 stops for a
  non-permissive dependency; the vendored files are BSD, ISC, MIT and
  public domain. The LGPL parts of openlibm are `test-double.c` and
  `test-float.c`, which are not vendored. `src/libm/LICENSE.md` carries
  upstream's text and `src/libm/PROVENANCE` names the commit.
- **The vendored sources are one translation unit, and their statics are
  scoped by generated headers.** Upstream compiles each separately, so
  eight files declare their own `static const double one`. One TU is
  deliberate -- it is one set of 3.5's flags -- so rather than renaming
  statics inside someone else's code, `<file>.pre.h` and
  `<file>.post.h` rename them with the preprocessor for the length of
  each include. The names come from `nm` on an unoptimised build of the
  file, so the list cannot drift from what the file declares.
- **Ten left shifts in the vendored code were undefined C99 and are
  cast.** Shifting a negative int is undefined before C++20, and four of
  these fire on arguments as ordinary as `exp(-1)`; this project runs
  UBSan with `halt_on_error`. The casts change no bit on any
  two's-complement machine and the corpus is byte-identical before and
  after. Listed one site at a time in `SHIFTFIX`, and a row that stops
  matching after an upstream update is a hard failure rather than a
  silent skip.
- **`math.log`'s base-2 and base-10 special cases are kept.** They make
  `log(8, 2)` exactly 3 rather than a ratio of two logarithms; the ratio
  form is inexact for eight of the first sixty powers of two.
  `test_libm.lua` counts them, so the special case cannot be dropped
  quietly.
- **Subagents were not used.** 0.1 permits them for a parallel cross-target
  gate at a milestone boundary and one review pass of a diff. The gate here
  runs in minutes sequentially on one machine, and a second agent reading the
  same diff would have cost more than it found.

- **A4's milestone lines were in the wrong block, and are moved.** A1, A2
  and A3 appended to section 10's *template* -- the fenced example of what
  a status block looks like -- rather than to the live `## Status` at the
  bottom of this file, where A0's line and every decision went. Other
  sessions read `## Status`, so three milestones were recorded where B and
  C would not find them. The template is back to its original two lines and
  the entries are in the list they belong to; no wording changed except
  three first lines reflowed to fit.
- **`<deterministic>` (4.6) did not land, and the reason is not the
  parser.** The attribute is easy; what it has to consult does not exist.
  `doc/Analyzer.md` says in its own words that the determinism verdict is
  specified and unbuilt -- no taint sources, no propagation over the call
  graph, no three-valued answer -- so an attribute wired today would run an
  analysis that returns nothing and would therefore accept every function.
  That is worse than no form: principle 2 says determinism is *reported*,
  and a marker asserting a property nothing checks reports a falsehood.
  A3 already recorded the same finding when it corrected the taint list.
  Owner: the verdict is a milestone of its own, and `<deterministic>` is a
  short follow-on once it exists.
- **A `switch` expression's subject must begin on the same line as
  `switch`.** This is the first contextual keyword this tree puts at an
  expression position, and an expression can end a statement, so
  `local a = switch` followed by `switch (1)` on the next line would read
  the first as introducing an expression whose subject is the second --
  a stock Lua program changing meaning, which principle 1 forbids and
  `test_interop` already pinned. A name followed *on the same line* by
  another name was always a syntax error, so the line rule settles it with
  nothing lost: the arms may still be on lines of their own. The statement
  form is untouched; it never meets the ambiguity.
- **The expression form is `case v: e` and `else e`, not `case v then e`
  and `default`.** The proposals spell it with the colon, and the two forms
  should not be confusable: nothing in the expression closes with `end`, so
  the punctuation is what tells a reader which shape they are in. `default`
  at that position is refused by name with the substitute, rather than by a
  generic parse error.
- **Slicing is `dv.slice`, a helper, and not a new metamethod slot.** 4.4
  asks for exactly this. What a range means depends on the value -- a view
  for an `array`, a substring for a string, a copy for a table -- and the
  lookup happens in C, so `ltm.c` is untouched and the core patch series
  does not grow. A plain table gets a copy and not a view: a form that
  sometimes aliased and sometimes did not would be worse than one that
  never does.
- **`export` is a hidden local, not a global or a registry entry.** A chunk
  that exports anything returns its module table, and the table is a local
  named `(export)` -- parenthesised, so no source name can collide. Two
  chunks loaded into one state cannot see each other's exports and nothing
  needs cleaning up if a chunk raises. An explicit top-level `return` in
  such a chunk is refused rather than reconciled: two returns would mean
  the exports were dropped on one path.
- **`export` binds a local *and* sets a field.** A chunk that exports a
  function usually also calls it, and a form that only set a field would
  make the chunk reach for a global to call its own function. Only at the
  top level of a chunk: inside a function the table is not in scope, and
  inside a block the local would have gone out of scope before the chunk
  returned.
- **A `for` pattern is one pattern and no extra names.** `for {a}, k in
  ...` would have to say which of the two the iterator's first value
  feeds, and there is no obvious reading. The control variable is hidden
  (`(for pattern)`) and the pattern's names are read out of it at the top
  of each iteration, inside the body's scope -- so a closure made in the
  body captures that iteration's values, which `test_tierb` checks.
- **Statement-level `[a, b] = [b, a]` did not land.** 4.2 lists it, but it
  is a second form -- `[...]` as a positional constructor -- rather than
  destructuring, and nothing else here needs one. It is also the one form
  in 4.2 that is not free the way the others are: a leading `[` at
  statement start can continue the previous statement's expression, the
  way `(` does in stock Lua, so it changes what an existing program's
  error says even where it cannot change what it means. Owner: say if the
  swap form is wanted and it becomes its own milestone.
- **`lparser.h` is still pristine, and `export`'s state lives in
  `LexState`.** The module table's variable index wants to be in
  `FuncState`, which would put `lparser.h` into the patch series for the
  first time. `export` is a chunk-level form and there is one main
  function per parse, so `LexState` holds it exactly as well. Principle 3
  decided this.
- **`luaX_lookahead` refuses to be asked twice, and the `switch` predicate
  is asked twice.** `field` looks ahead for a `=` before `listfield` ever
  reaches the expression, so `{switch c case 1: ...}` tripped the
  assertion in the debug build -- and would have read a stale token in a
  release one. `peekahead` reads the buffered token when there is one.
  Worth knowing for any later contextual keyword at an expression
  position: this is the trap.
- **The README is not updated for Tier A or Tier B.** It is a declared
  human surface and it documents the syntax the *released* build ships;
  these forms are on a branch whose CHANGELOG entries stay `unreleased`,
  per 0.3. Owner: the README and `doc/Guide.md` want a pass when the build
  is cut, and that pass is one edit rather than five.
- **Subagents were not used for A4 either.** Same reading as A3: the gate
  runs sequentially on one machine in minutes, and the review pass 0.1
  permits was done by reading the diff -- which is what found three dead
  locals and the two `(void)` casts hiding them.

- **`c128` is a guest-side dtype and is not in `dv.h`.** 3.1 spells
  `dv_array_adopt`'s dtype argument out as "0=f64 1=i64 2=u8", and that
  header is what B compiled against at A0; a fourth number would move a
  published contract. It would move it for a type no host has a buffer of,
  too -- complex data on a wire is pairs of doubles, which is `f64` and then
  `array.complex`. `diluvium_array_adopt` refuses dtype 3 by name rather
  than by falling off a switch, and `dv.c`'s comment saying stage 2 would
  add it here is corrected to say why it did not. 0.2 lists a `dv.h` change
  beyond section 3 as a stop condition; this is the reading that does not
  need one.
- **`dvn_check` now means "a real array" and `dvn_checkany` means "an
  array".** Adding a dtype to a library with forty kernels is a question of
  what happens to the thirty-eight that cannot mean anything for it. Making
  the *default* accessor refuse `c128` answers it once: every elementwise
  operator, reduction, sort, grouping and linear-algebra entry refuses a
  complex array with a sentence naming the two functions that convert it,
  and none of them had to grow a branch. The alternative -- letting `c128`
  through and reading it as bytes, which is what the old `default:` arm of
  the accessors would have done -- is the failure this was built to make
  impossible.
- **`a[i]` and `a[i] = v` are refused on a `c128` array.** `__index` yields
  one value and an element is two, so indexing could only return the real
  part, and assigning could only zero the imaginary one. Both say so and
  point at `array.get`/`array.set`, which take and return the pair.
- **The FFT computes twiddles per index; the NTT walks its root.** They look
  inconsistent and are not. A float recurrence accumulates error that
  depends on how many steps preceded it, so the same twiddle would differ
  between an n=1024 transform and the n=2048 one containing it -- and
  between a backend that vectorised the recurrence and one that did not,
  which is the thing a reproducible tier cannot allow. Modular
  multiplication is exact, so the NTT's recurrence is the same number
  however it is reached, and computing each root by exponentiation instead
  would cost a log for nothing.
- **`rfft` is the full transform, truncated.** The half-length complex trick
  halves the work and gives different last bits. What this stage owes is a
  fixed answer, not a fast one; the saving is recorded as available and not
  taken. `test_transform` checks the two agree bit for bit, so the day it is
  taken, that line is what has to change.
- **`magnitude` is `sqrt(re*re + im*im)`, not `hypot`.** `hypot` is not
  correctly rounded and is not one of the functions stage 1 vendored, so a
  platform's would put a cross-target difference back into a value the
  reproducible tier pins. Multiplication, addition and `sqrt` are each
  correctly rounded by IEEE 754. The cost is `hypot`'s scaling: a magnitude
  overflows here when the squares do, at about 1.3e154, which is stated in
  the code.
- **An exact convolution refuses rather than wraps.** The NTT gives the true
  answer only while it never exceeds the ring, so the bound
  `max|x| * max|y| * min(#x,#y)` is checked against half the prime before
  any work -- by division, so the check itself cannot overflow -- and a
  program past it is told the three numbers rather than handed a residue.
  `math.mininteger` is tested before anything negates it, because
  `-LUA_MININTEGER` is undefined and this project runs UBSan with
  `halt_on_error`.
- **No complex arithmetic.** `+`, `*` and the reductions over `c128` would
  be a second implementation of every kernel in `dnumeric.c` for a use stage
  2 does not have: the one place complex multiplication was actually needed
  is inside the convolutions, where it is four lines. Owner: say if a
  complex elementwise layer is wanted and it becomes a milestone.
- **Power-of-two sizes, and a refusal that names the length.** The spec's
  own bail-out defers Bluestein and makes explicit padding the v1 contract.
  A length that is not a power of two is refused with the number it would
  have needed (`pad to 128`), rather than rounded up into an answer about a
  different signal.
- **Stage 2 stayed in `dnumeric.c`.** A separate file would have to see
  `dv_array`, which is private to that translation unit and is what keeps a
  view's invariants in one place. The file grew by about 900 lines and its
  surface block grew two fan-out entries; splitting it would trade an
  encapsulation that is load-bearing for a line count that is not.

- **A class's field defaults come before its first method.** A default is an
  expression, and a single-pass parser cannot park one and re-emit it inside
  a constructor it has not read yet. Compiling them where they stand, into
  one hidden function taking `self`, is the answer that needs no second
  pass; a field after a method is refused with that sentence rather than
  accepted into nothing. 5.1's own example is written fields-first, so the
  restriction costs the natural style nothing.
- **The defaults function is a hidden local *and* a table entry.** The local
  is what a declared `new`'s prologue calls, so no name a program could
  shadow -- not even the class's own -- is on that path. The entry
  (`Class["(defaults)"]`) is what `dv.class`'s default constructor reads for
  a class that declares no `new`. Not `__`-prefixed, deliberately: `dv.class`
  copies a parent's `__` entries into the child, and a copied defaults
  function would apply the parent's fields twice.
- **A parent's default wins over a child's for the same field name.** The
  prologue runs before the body, so `super(...)` -- and with it the parent's
  own prologue -- runs after the child's defaults. That is 5.1's stated
  order ("parent defaults apply when `super(...)` runs") read literally.
  Child-wins would need the chain applied root-first, which is what most OO
  languages do; recorded because it is the one place the spec's order and
  the conventional one differ. `test_class` pins both directions, so
  changing it is one assertion.
- **`super:m(...)` is refused by name.** `super.m(...)` already passes
  `self`, so the colon form would pass the parent table as `self` and
  quietly call the method on the wrong object. Refused with the form to use
  instead.
- **`super` is effectively reserved inside a class body.** 5.1 says it is
  special there, so a `local super` declared inside a method still parses
  but every *read* of it resolves to the parent. Recorded rather than
  guarded: refusing the declaration is more machinery for a name nobody
  writes inside a class, and outside one `super` is an ordinary name, which
  `test_class` checks.
- **`@` binds a following name as a field.** `@balance` is `self.balance`,
  which is the form's whole purpose, and the consequence is that a bare `@`
  at the end of a statement takes the next statement's first name. No stock
  Lua program contains `@`, so nothing that parsed before parses
  differently, and the failure is a compile error rather than a silent
  change of meaning.
- **`dv.class` is C, not emitted bytecode.** Copying a parent's metamethods,
  installing two metatables and a default constructor is about thirty lines
  of C or a couple of hundred instructions this file would have to emit and
  a reader would have to decode. It is also where the gotcha belongs: 5.1
  asks for the raw-metamethod-lookup problem to be handled once in the
  desugar rather than by every program.
- **`@` works in any method, not only a class's.** It resolves `self` as an
  ordinary name and refuses at compile time when there is none, so
  `function obj:m() return @v end` works on a hand-written table. Nothing in
  5.1 asks for that; it falls out of the desugar and is better than a form
  that means one thing in a class and nothing outside one.

- **The reproducible tier does not pin the sign of a NaN, and the corpus
  should never have implied it did.** CI's `Numeric (macos-arm64)` job caught
  it on PR #33: one line of 101 differed, the two NaNs in the `sort` line,
  `fff8000000000000` on x86-64 against `7ff8000000000000` on aarch64. Both
  are correct -- IEEE 754 does not interpret the sign of a NaN and does not
  say which one an invalid operation produces -- and the corpus was building
  its NaN with `0.0 / 0.0`, so it was pinning the FPU's choice rather than
  the program's. The kernels are right: `sort` moves a value without touching
  its bits, and `dvn_key` canonicalises a NaN where an answer *has* to match
  everywhere, which is why `group_zero_nan` passed on both targets all along.
  Fixed in the corpus, by building the NaN from its bits, plus one new line
  asserting the portable half -- whatever NaN a target's FPU makes still
  sorts last. The limit is now written into `dnumeric.c`'s list of what the
  tier costs, beside the reduction order and the total ordering, because it
  is a caveat a program reading bit patterns needs. Checked both ways
  locally: flipping the computed NaN's sign leaves the output byte-identical,
  and flipping the pinned one still changes it, so the line has not become a
  no-op.

- **Session B could not reach any of A2's work, and the two gaps were both
  mine.** B moved DRT's pin onto this branch and found that the safe
  `diluvium` crate had no `[features]` section, so an embedder taking it got
  `diluvium-sys` with defaults and a core reporting no `numeric`; and that
  `dv_array_adopt` was declared in `-sys` and wrapped nowhere, so a host could
  carry a column to the boundary and not hand it over. Both are what A0
  promised -- "the interface B compiles against" -- and neither was caught
  here, because every check A0 through A6 ran was a check of the *core*.
  Nothing exercised the path an embedder actually takes: `diluvium` the safe
  crate, with the feature on. `bindings/rust/diluvium/tests/adopt.rs` is that
  check now, and it reads `library_features()` rather than assuming, so one
  file means something in both configurations.
- **`dv_reply_blob` stays out of `dv.h`, and section 2's table row is the
  thing that is wrong.** A0 recorded that 3.1 is the authority where it and
  section 2 disagree, and asked B to say if that was wrong. B's answer settles
  it from the other side: DRT compiles no C at all -- no `.c`, no `.h`, no
  build script -- so the entry point section 2 names has no caller on either
  side of the boundary. Owner: the row is the plan's to correct.
- **Two defects in `dv_array_adopt`, found while wiring B's request, reported
  and then fixed on request in
  `e54e000a6d62e5aa0b4dd13fe552b1144a998e08`.** The adopted bytes were never charged, so
  `dv.h`'s "they count against the instance's memory limit" was false on the
  adopt path -- an 8 MB column into a 256 KB-budgeted instance was accepted
  and moved the counter 120 bytes. And every way of putting the bytes in front
  of the guest allocates, inside a call with nothing protected above it, so an
  allocation failure reached the panic function and aborted the host:
  reproducible at 240 KB against a 256 KB budget with the feature off, and on
  the adopt path too, where the array's header is the allocation. Both are
  fixed; what each cost is below.
- **The charge and the credit are a pair, and the pair lives in
  `dnumeric.c`.** Charging alone walks `mem_used` upward forever, which is the
  drift `dv_release_adopted`'s own comment exists to warn about, so the credit
  is not optional. It is made where ownership ends -- `dvn_gc`, the only place
  a `DVN_OWN_EXTERN` buffer is freed -- and the charge where ownership is
  taken, the line in `diluvium_array_adopt` that sets `DVN_OWN_EXTERN`. Beside
  each other and beside the field they mirror, so writing half of the pair is
  not a thing the file lets you do. Both reach `dv_instance` through a new
  `diluvium_memory_charge` / `diluvium_memory_credit` seam in `dv.c`, declared
  in `dnumeric.h` beside the budget seam it copies and deliberately not in
  `dv.h`: no published symbol, no 0.2 stop. `dv_release_adopted`'s balancing
  add stopped touching `mem_peak` in the same change -- a column that was
  copied or refused was never the instance's, and a peak that said otherwise
  told a supervisor to size this child for memory it never held.
- **A handover that cannot be made returns 1 with nothing pushed, and 3.1's
  "only on invalid arguments" is now two cases rather than one.** No new
  return value: a host switching on 0/1 reads the same two numbers, and B
  compiled against this header. What is new is that `dv_last_error` is
  non-NULL exactly when nothing was pushed, which is a discriminator a host
  can actually evaluate -- the stack depth 3.1 named is not visible through
  this ABI. `dv_array_adopt` clears the error after validating its arguments
  and before the handover to make that test exact. Prose inside section 3, no
  signature or ABI-version movement, so decide-record-proceed rather than a
  stop; the alternative it replaces is aborting the host process, which is not
  a contract worth preserving.
- **A column larger than the remaining budget is still taken.** The limit is
  enforced on allocations and a handover is not one, so the instance simply
  ends up over its limit and the guest's next allocation fails with
  `dv_exceeded` set -- the same shape as every other way of going over budget.
  Refusing up front would have been friendlier and was not done: it duplicates
  `dv_alloc`'s limit test in a second place, which is the kind of second copy
  this file's own comments blame for the last budget defect, and `dv_memory`
  right after the call already tells a host that cares. Written into 3.1.
- **A third thing was found and not fixed: an adopted value is never
  consumed.** `dv_resume` pops `inst->pending` values before it resumes, and
  an adopted value sits above them, so each adopt-then-resume round drops the
  adopted value and leaves one of the park's own results behind on the
  thread's stack. Harmless today -- nothing reads those slots and the resume
  takes its arguments from the top -- but it is the reply wiring 3.1 stages
  this call for, and that wiring does not exist yet. Outside what was asked
  for here. Owner: whoever lands the hostcall reply path.
